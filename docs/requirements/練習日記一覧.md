#### 認証（新しく入った土台）

- アプリ全体が 1 つのパスワードで保護されている（`server/auth.mjs`）。セッションは httpOnly Cookie。
- `server/index.mjs` は `/api/auth/*` を定義した直後に `app.use('/api', requireAuth(db))` を置いている。**それより後ろに定義された `/api/*` はすべてログイン必須**で、日記の取得・保存（`GET` / `PUT /api/activities/:id/note`）も、閾値やシューズも、この内側にある。つまり日記の本文は現時点で既に認証で守られている。
  - 例外的に `POST /api/auth/change-password` だけは `app.use` より前で、ハンドラ個別に `requireAuth(db)` を付けて保護している。
- パスワード未設定（初回セットアップ前）の場合、`requireAuth` は 401（`setup_required`）を返す。つまり未設定状態でも `/api/*` から日記本文は取得できない。
- 認証が掛かっているのはサーバー API だけで、静的ファイル配信（`dist` の HTML / JS）は保護されていない。画面のコード自体は誰でも取得できるが、日記本文は API 越しにしか得られないため、本文が未認証で読める経路は無い。
- 画面側（`src/App.tsx`）は起動時に `GET /api/auth/status` を叩き、未ログインなら `LoginView` を出してタブも各画面も一切描画しない。ログインはハッシュを書き換えないため、`#/xxx` を直接開いて未ログインだった場合は、ログイン成功後にそのタブがそのまま表示される。
- `src/api.ts` の `toJson` は `/api/auth/` 以外の API で 401 を受け取ると `UNAUTHORIZED_EVENT` を発火し、`App` がログイン画面へ戻す。セッション切れ時の挙動は全画面共通。
- `GET /api/auth/status` 自体が失敗した場合（サーバー停止など）、`App` は `{ configured: false, authenticated: true }` として扱い、認証なしで画面を描画する。したがってサーバーが落ちていてもタブと各画面は表示され、各画面が個別に取得失敗を表示する（例: 保存済み一覧は「保存サーバーに接続できません（保存機能なしで利用できます）」）。

### 困っていること

「あのとき何を書いたか」を読み返すのに、心当たりのアクティビティを 1 件ずつ開いて FIT を再解析させるしかない。過去の記述を横断して眺めることも、キーワードで探し当てることもできない。日記は書きっぱなしで、振り返りに使えていない。

また、日記本文だけが並んでいても「何の練習の日記か」が分からない。読み返すときに知りたいのは文章そのものだけでなく、「この距離を走ったときに何を感じていたか」という、練習内容と記述の対応関係である。

### 認証との関係

日記一覧は「既存タブと同じ扱い」にする。日記一覧だけが特別な認証の扱いになることは避ける。

- 日記一覧の画面は、既存タブと同じくログインの内側に置く。未ログインではログイン画面が出て、一覧も本文も表示されない。
- 一覧が使うサーバー API も、既存の `/api/*`（日記の取得・保存を含む）と同じく**認証の内側**に置く。未ログインのまま直接叩いても日記本文が返らないこと。新しいエンドポイントを設ける場合も同様。
- 未ログインで `#/diary` を直接開いた場合は、既存タブと同じ扱いでよい。ログイン画面を出し、ログイン成功後にそのまま日記一覧を表示する（現在の `App.tsx` の作りでは、日記タブを足せば自動的にこうなる。この挙動のための追加実装は想定していない）。
- 一覧を表示中にセッションが切れた場合も、既存タブと同じくログイン画面に戻る。日記一覧だけ独自のエラー表示や挙動にしない。
- 認証の仕組み自体（パスワード、セッション、ログイン画面、パスワード変更）には手を入れない。

### 一覧の見え方

- 日記が保存されているアクティビティだけを縦に並べる。日記が無いアクティビティは出さない。
- 並び順はアクティビティ日付の新しい順で固定。
- 各項目には、本文に加えて次を表示する。目的は「一覧を眺めたときに何の練習の日記か見分けられること」と「練習内容と本文を並べて読めること」。
  - **アクティビティの日付**
  - **競技種目**。スイム／バイク／ランのどれか（あるいは複数）が分かること。見せ方（絵文字か文字ラベルか）は問わない。
    - トライアスロンのように複数種目を含むアクティビティでは、含まれる種目がすべて分かること。
  - **主要指標**。距離・タイムなど、その練習の規模が分かる数値。
    - 種目ごとに何を出すか（ランは距離とタイム、スイムは距離、バイクは距離と時間、など）は、既存画面での見せ方・単位・書式に合わせて**設計側が決めてよい**。ここでは指定しない。
    - 複数種目を含むアクティビティで指標をどこまで並べるかも設計側の判断。最低限、種目が分かることを満たせばよい。
    - .fit を再解析せずに得られる範囲の値でよい（背景に書いたとおり、サマリに既に含まれている）。
- 本文は Markdown として整形して表示する。到達点は「自分が書いた構造が、構造として読める」こと。
  - 対応する記法の範囲は **GFM（GitHub Flavored Markdown）相当**とする。具体的には以下が整形されて読めること。
    - 見出し（【スイム】のように自分で書き分けた区切りが、見出しとして見える）
    - 箇条書き（番号なし・番号つき）
    - 強調
    - 引用
    - リンク
    - コード（インライン・コードブロック）
    - 水平線
    - **表**（練習メニューを表形式で書きたい）
    - **チェックボックス**（やることリストを書きたい）
  - `#` `-` `|` `- [ ]` といった記法の記号が、生のまま画面に残らない。
  - ※ どう実現するか（ライブラリを導入するか、自前で書くか、何を使うか）は設計側の判断。ここでは決めない。
- 本文は冒頭数行に畳まない。展開操作なしで、整形された本文を最後まで読める状態にする。
- 各項目から、その日記が紐づくアクティビティの画面へ移動できる。移動先では従来どおり指標を見て、日記を編集・保存できる。
  - アクティビティを開くと .fit の再取得・再解析で待ち時間が出る点は、利用者が承知の上で許容している。設計側で無理なく軽減できるなら軽減してよいが、必須ではない。

### 検索

- キーワード入力欄をひとつ置く。この欄だけで本文検索と期間の絞り込みを兼ねる。
- 入力すると該当する日記だけが一覧に残る。空にすると絞り込みが解除され、全件表示に戻る。
- 検索対象は「日記の本文」と「アクティビティの日付」の 2 つ。1 つの語について、どちらかに一致すればヒット扱い。
  - 例: 「2025-07」と打つと、2025 年 7 月のアクティビティの日記に絞れる（本文にその文字列が無くてもヒットする）。
  - 例: 「LT走」と打つと、本文にその語を含む日記に絞れる。
- 日付へのマッチは **`YYYY-MM-DD` 表記への部分一致だけ**でよい。「2025/07」「7月」といった別表記は対応しない。
- マッチは部分一致。大文字小文字の違い、全角半角の違いは無視する。
- スペース区切りで複数語を入れた場合は AND。すべての語にヒットした日記だけが残る。
- 本文はどの記法の中に書いた語も検索対象に含める。表のセル内やチェックボックス項目内に書いた語でもヒットする。
  - ただし `**LT走**` のように強調記号をまたぐ語まで拾えるかは、整形との兼ね合いで設計側の判断とする。
- ヒットした語は本文中でハイライトして示す。
  - 見出しや箇条書きなど、**整形された要素の中にある語もハイライトされるのが望ましい**。
  - ハイライトと整形表示の両立が技術的に難しい場合は、**整形表示を優先する**。その場合でも表示が壊れてはならない（生の記法に戻る・レイアウトが崩れるといったことが起きない）。どう両立させるかは設計側の判断。
- 一致する日記が 1 件も無い場合は「該当なし」と分かる表示を出す。

### 規模の前提

- 日記の件数は数十〜百件規模を想定する。この規模で快適に動けばよい。

## やらないこと

- **日記を書く導線の作り直し**。日記の入力・保存は従来どおりアクティビティ画面の `DiaryCard` が担う。入力欄はプレーンな `textarea` のままでよい。
- **一覧上での日記の直接編集・保存**。日記一覧は閲覧専用。直したくなったらアクティビティ画面へ移動する。
- **Markdown の編集支援**（プレビュー付きエディタ、記法のツールバー、入力補完）。整形表示は一覧側の話であり、書く側には手を入れない。
- **チェックボックスを一覧上で操作できるようにすること**。チェックボックスは「整形されて見える」だけでよい。一覧はあくまで閲覧専用なので、クリックで状態を切り替えたり、その結果を保存したりはしない。
- **GFM の範囲を超える記法への対応**（生 HTML の埋め込み、数式、脚注、独自拡張記法など）。
- **「2025/07」「7月」など `YYYY-MM-DD` 以外の日付表記での検索**。
- **一覧へ戻ったときのキーワード復元**。アクティビティ画面から戻ったときにキーワードが消えていても許容する。
- **競技種目・期間・シューズタグによる絞り込み UI**。今回は設けない。期間の絞り込みはキーワード欄の日付一致で代用する。
- **一覧項目上でのグラフ・チャート表示**。数値を文字で出せば足りる。
- **アクティビティに紐づかない日記**（練習していない日や、FIT を取り込んでいない日の日記）。今回のスコープ外。必要になったら別途起票する。
- **日記が無いアクティビティを一覧に出すこと**（書き漏らしに気づくための表示）。今回は日記があるものだけを扱う。
- **並び順の切り替え UI**（古い順、日記の更新日時順など）。新しい順で固定。
- **ヒット箇所の前後だけを抜き出した抜粋表示**。本文は常に全文を整形表示するため不要。
- **日記以外のテキストを検索対象にすること**（ファイル名、シューズタグ名など）。検索対象は本文と日付のみ。表示する種目名・指標は検索対象に含めなくてよい。
- **FIT の指標を条件にした検索**（距離が 10km 以上、平均心拍が 150 以上など）。今回は日記を探すための機能であり、アクティビティ検索ではない。
- **あいまい検索・類似検索・LLM による要約や自動タグ付け**。
- **日記へのタグ付け・カテゴリ分類・お気に入り・ピン留め**。
- **日記のエクスポート・インポート・印刷・バックアップ**。
- **日記の編集履歴やバージョン管理**。
- **複数ユーザー対応・共有・公開**。利用者は作者ひとり。
