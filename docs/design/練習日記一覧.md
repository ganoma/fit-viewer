### 解釈が割れそうな箇所についての本設計の解釈

1. **「【スイム】のように自分で書き分けた区切りが見出しとして見える」**（要件「一覧の見え方」）
   → 実データ `data/cde31878c7a31609.note.md` を読んだところ、この日記に Markdown の `#` は**使われていない**。
   `【スイム】…` で始まる段落が空行区切りで並んでいるだけである。
   したがって「`【】` を見出しに変換する独自ルール」は実装しない（要件の「やらないこと」の「独自拡張記法」に当たる）。
   受け入れ条件「書いた構造のまま読める」は、**段落の区切りと改行がそのまま保たれて読める**ことで満たす。
   今後 `#` を書けば見出しになる、という状態にする。

2. **単一改行（ソフトブレイク）の扱い** → 要件に記述が無い。素の GFM 仕様では単一改行は無視されて段落が繋がるが、
   入力欄が素の `textarea`（`src/DiaryCard.tsx`）である以上、書いた人の見た目は「改行したところで改行される」である。
   GitHub のコメント欄と同じ挙動（単一改行 = `<br>`）に寄せる方が「書いた構造のまま読める」に適うと判断し、
   `remark-breaks` を入れて**単一改行を改行として描画する**。末尾の「要件への質問 1」に非ブロッキングの確認として置く。
   なお実データの日記は空行区切りなので、この判断で既存日記の見た目は変わらない。

3. **検索対象のテキスト** → `.note.md` の**生テキスト**（Markdown 記法の記号を含む文字列）を対象とする。
   要件で「`**LT走**` のように強調記号をまたぐ語まで拾えるかは設計側の判断」とされているため、
   `**LT**走` を `LT走` で引っ掛けることはしない。表のセル内・チェックボックス項目内の語は生テキストにも
   そのまま含まれるので、受け入れ条件（表のセル内の語でヒット）は満たせる。

4. **ハイライトと整形表示の両立** → 両立させる（後述の rehype プラグイン方式）。整形表示を犠牲にしない。
   ただし記法記号をまたぐ語はハイライトされない（3 の帰結）。要件の許容範囲内。

5. **一覧の日付表示形式** → `YYYY-MM-DD`（例 `2026-07-04`）で出す。
   要件の受け入れ条件が「画面に `2026-07-04` と出ているなら『2026-07』で残る」と書式まで含めて書いているため、
   これは要件側で決まっているものと解釈した。既存の保存済み一覧の `toLocaleDateString('ja-JP')`（`2026/7/4`）とは
   書式が異なるが、**見えている文字列と打つ文字列を一致させる**ことを優先する。

6. **日付の基準（JST）** → 要件 Q18 のとおり JST。ただし実装上は**クライアントのローカルタイム**で算出する
   （作者の環境では JST）。理由は「方針 6」に書く。

7. **主要指標の中身** → 要件で設計側に委ねられている。既存画面の単位・書式に合わせて種目ごとに決める（方針 5）。

### 1. データ取得は `GET /api/notes` を新設して 1 リクエストで済ませる（前版から据え置き・再確認済み）

現状 `GET /api/activities`（`server/index.mjs` 190-210 行）は `hasNote` の真偽しか返さず、
本文は 1 件ずつの `GET /api/activities/:id/note`（336-341 行）しかない。100 件分ループすると 100 リクエストになるので採らない。
`/api/activities` に本文を相乗りさせるのも、この API は `ActivityView` / `TrendsView` / `HomeView` の 3 画面が叩く共通経路で、
そのどれも本文を必要としないため採らない（要件の「やらないこと」にも「既存の応答形状・並び順を変えない」とある）。

**日記一覧専用のエンドポイント `GET /api/notes` を足す。** サマリ（`<id>.json`）と日記（`<id>.note.md`）を
サーバー側で突き合わせ、日記のあるものだけを `startTime` の降順で返す。100 件でも数百 KB 程度なので全件返して問題ない。

**並べ替えはサーバー側で降順に確定させる。** 既存 `/api/activities` は昇順で返し `ActivityView` が
`[...saved].reverse()` して見せているが、その流儀は踏襲しない（`/api/notes` は日記一覧専用で、
「新しい順」以外の使い道が無いため、クライアントに並べ替えを持たせる理由が無い）。
`startTime` は UTC の ISO 文字列で、ISO 文字列の辞書順は時刻順と一致するため、タイムゾーンに関係なく並びは正しい。

**データの置き場所についての判断**: 新しい永続データは増やさない。日記本文は既存どおり `DATA_DIR` の
`<id>.note.md`（ファイル）、指標は `<id>.json`（ファイル）から読む。SQLite（`fitviewer.db`）には**何も足さない**。
今回の機能は「既にあるファイルを読んで束ねるだけ」で、新しいメタデータが発生しないため。

### 2. `GET /api/notes` は `app.use('/api', requireAuth(db))` より後ろに置く（★今回の最重要点）

`server/index.mjs` は 163 行で `app.use('/api', requireAuth(db))` を置いており、
**この行より後ろに定義された `/api/*` だけが認証の内側**にある（`/api/auth/*` は前、`change-password` だけ個別に付与）。
要件は「一覧が使う API も既存の `/api/*` と同じく認証の内側に置くこと」「未ログインで直接叩くと 401」を明示しているので、
`GET /api/notes` は 163 行より後ろに置く。

**具体的な配置**: 既存の `app.get('/api/activities/:id/note', ...)`（336 行）の**直前**に置く。
日記関連のルートが隣接し、どこに足したか後から追いやすい。静的配信の catch-all（378-381 行）より前なので競合しない。
`/api/notes`（2 セグメント）は `/api/activities/:id/note`（4 セグメント）とパターンが重ならない。

`requireAuth` はパスワード未設定時にも 401（`setup_required`）を返すので、
受け入れ条件「パスワード未設定の状態でも 401」も自動的に満たされる。ハンドラ側に認証コードは一切書かない。

### 3. 絞り込み・ハイライトはクライアント側で行う（前版から据え置き・再確認済み）

サーバーに `?q=` を持たせても、ハイライトのために結局クライアント側にも同じ照合処理が要る（二重実装）。
全件をクライアントに持たせ、絞り込みもハイライトも `src/diarySearch.ts` の同じ正規化関数で行う。

正規化は **NFKC 正規化 + 小文字化**。これで大文字小文字（`LT` / `lt`）と全角半角（`LT` / `ＬＴ`）、
全角スペース区切りが一度に吸収できる（実際に `node` で確認した: `'ＬＴ走　テンポ'.normalize('NFKC')` → `'LT走 テンポ'`、
`'　'.normalize('NFKC')` → `' '`）。
ハイライトのために「正規化後インデックス → 元文字列インデックス」の対応表が要るので、
**1 文字ずつ正規化して対応表を作る**（詳細は「データ構造」）。

キーワード入力の反応性は React 19 の `useDeferredValue` で担保する。入力自体は即座に反映し、
絞り込みと再整形は遅延させる。デバウンス用の追加依存は入れない。

### 4. Markdown 整形は `react-markdown` + `remark-gfm` を導入する（前版から据え置き・バージョン再確認済み）

要件は GFM 相当（表・チェックボックス含む）まで要求しているので、自前実装は割に合わない（「却下した案」参照）。
**実装役への明示的な指示として、以下の依存追加を許可する。**

```
npm install react-markdown@10.1.0 remark-gfm@4.0.1 remark-breaks@4.0.0
```

- `dependencies` に入れる（既存の react / plotly と同じ扱い。バンドル対象）。`--save-dev` は付けない。
- バージョンは 2026-09-15 時点の最新を `npm view` で確認済み。`package.json` には `^` 付き（npm 既定）で入る。
- **`package-lock.json` の更新も必ず成果物に含める**。`Dockerfile` の build ステージ・runtime ステージがどちらも
  `npm ci` を使っており、lock が更新されていないとコンテナビルドが失敗する。
- `react-markdown@10.1.0` の peerDependencies は `react: >=18` / `@types/react: >=18`。
  本リポジトリは React 19.2 / @types/react 19.2 なので警告なく入る（確認済み）。
- 追加するのはこの 3 つだけ。**`rehype-raw` と `rehype-sanitize` は入れない**（理由は次項）。

**サニタイズの要否**: `react-markdown` は `dangerouslySetInnerHTML` を使わず、Markdown を直接 React 要素に変換する。
本文中の生 HTML は既定でエスケープされて「ただの文字」として表示され、DOM にはならない。
リンク URL も既定の `urlTransform` が `javascript:` などを落とす。
したがって **HTML 文字列を組み立てる箇所が一切無く、サニタイザは不要**。
要件の「生 HTML の埋め込みは対象外」とも一致する。`rehype-raw` を足すとこの前提が崩れるので禁止する。

**バンドルサイズ**: 3 パッケージで min 換算おおよそ 150KB 前後（gzip 50KB 前後）の増加。
現行の `dist/assets/index-*.js` は plotly.js を含んで **4.8MB**（実測）なので、増分は数 % に収まる。
個人用ツールとして許容範囲と判断した。

**チェックボックス**: `remark-gfm` のタスクリストは `<input type="checkbox" disabled>` として出力される。
既定で操作不可なので、要件「一覧上で操作できるようにしない」は追加実装なしで満たされる。

### 5. ハイライトは「整形後のツリーのテキストノードを分割する」方式（前版から据え置き）

整形前の Markdown 文字列を `<mark>` で置換すると記法が壊れる。描画後の DOM を走査して書き換えると
React の再描画と競合する。どちらも採らない。

**`react-markdown` の `rehypePlugins` に自前の小さなプラグインを渡し、整形済みツリー（hast）の
テキストノードだけを分割して `<mark>` 要素に差し替える。** 要素の構造（表・リスト・見出し）には触らないので
レイアウトは壊れず、見出しや表のセルの中の語もハイライトされる。要件の「望ましい」状態を満たせる。

割り切った点（要件の指示に従い明記する）:

- **記法記号をまたぐ語はハイライトされない**。`**LT**走` に対して `LT走` で検索しても、テキストノードが
  `LT` と `走` に分かれているためハイライトされない（絞り込み側は生テキスト照合なので**一覧には残る**）。
- **記法記号そのものを検索語にした場合**（例: `|`、`**`）、生テキストには一致するので項目は一覧に残るが、
  整形後のツリーにその記号は存在しないためハイライトは付かない。**表示は壊れない**ので許容する。
- 正規化は 1 文字ずつ行うため、半角カナ + 濁点（`ｶ` + `ﾞ`）は `ガ` に畳まれない
  （文字列全体の NFKC なら畳まれるが、1 文字ずつだと `カ` + 結合濁点になる。`node` で確認済み）。
  絞り込み・ハイライトとも同じ関数を使うので挙動は一貫する。実用上ほぼ起きないため許容する。

### 6. 日付の JST 基準は**クライアント側**で担保する（今回追加した判断）

要件 Q18 の既定どおり、一覧の日付表示も日付検索も JST 基準にする。実装場所をサーバーにしない理由:

- `Dockerfile` にも `docker-compose.yml` にも `TZ` の指定が無い（確認済み）。
  本番コンテナの `node` はローカルタイム = UTC で動くため、**サーバーで日付文字列を組み立てると
  `b60ba4a371e4beb1`（UTC 2026-05-16 / JST 2026-05-17）のような例で 1 日ずれる**。
- 既存画面（`ActivityView`）の日付表示はブラウザのローカルタイムであり、クライアントで組み立てれば既存と揃う。

よって `/api/notes` は `startTime` を **UTC の ISO 文字列のまま**返し、
`YYYY-MM-DD` への変換はクライアントの `dateKey()` が一手に引き受ける。
表示にもフィルタにも同じ `dateKey()` を使うので、受け入れ条件「画面の日付と検索文字列が一致する」は
実装上ずれようがない構造になる。

### 7. 一覧項目に出す指標

`GET /api/notes` が返す `sports[]`（サマリ済み。.fit の再解析は不要）から、**種目ごとに 1 行ずつ**出す。
書式は既存画面の実コードに合わせる（下表の「合わせ先」は実読して確認した）。

| 種目 | ラベル | 出す指標と書式 | 既存の合わせ先 |
|---|---|---|---|
| running | `🏃 ラン` | `5.17 km` · `27:48` · `5:23 /km` · `146 bpm` | `ActivityView` の Distance（`(m/1000).toFixed(2)` + ` km`）、`fit.ts` の `fmtDuration` / `paceStr`、`ThresholdsView` の `/km` 表記 |
| cycling | `🚴 バイク` | `39.72 km` · `1:12:28` · `32.9 km/h` · `185 W` · `141 bpm` | `BikeDetails` の Avg Speed（`toFixed(1)` + ` km/h`）、Normalized Power（` W`） |
| swimming | `🏊 スイム` | `1459 m` · `32:39` · `2:14 /100m` · `149 bpm` | `SwimDetails` の Distance（`Math.round` + ` m`）、`pace100Str` + ` /100m` |
| その他 | `🏅 <sport>` | 距離（km）· 時間 · 心拍 | — |

- ラベル文言は `TrendsView` の `SPORT_SECTIONS.label`（`🏃 ラン` / `🚴 バイク` / `🏊 スイム`）と完全に一致させる。
- `null` / `0` の項目は出さない（既存の KPI 群と同じ考え方）。
- `paceStr` は速度が 3〜25 km/h の範囲外だと `'--:--'` を返すので、**`'--:--'` のときはペースを出さない**。
- 複数種目（トライアスロン）は **種目の数だけ行を並べる**。合計値は作らない（要件「最低限、種目が分かればよい」）。
- **ファイル名は出さない**。要件で検索対象外と決まっており、画面に出ていて検索に引っかからない文字列を
  作ると「なぜヒットしないのか」という混乱のもとになる。

### 8. ナビゲーション

`src/App.tsx` の `Tab` に `'diary'` を足し、`parseHash` に `#/diary` を足し、タブボタンを **⚡ 閾値 の後ろ**に置く。

**`navigate` の書き換えについて（前版の提案を現物で再判断した）**:
前版は「現在 3 分岐の入れ子三項なので switch にする」と書いていたが、現在は閾値タブが増えて**既に 4 分岐**である。

```ts
// 現在（src/App.tsx 40-51 行）
function navigate(tab: Tab, sport: string | null = null) {
  window.location.hash =
    tab === 'home' ? '/'
      : tab === 'activity' ? '/activity'
        : tab === 'thresholds' ? '/thresholds'
          : sport ? `/trends/${sport}` : '/trends';
}
```

ここに `diary` を足すと 5 段の入れ子三項になる。**書き換えの方針は維持する**が、根拠は
「読みにくくなるから」ではなく **同じファイル内の `parseHash` が `if` の並びで書かれており、
`switch` にすれば逆変換どうしが同じ形で並ぶ** ことに置く（`CLAUDE.md` の「既存の書き方に合わせる」に沿う）。
ハッシュ生成結果が 1 文字も変わらないことは下の対応表で確認する。

| `tab` | `sport` | 現在の出力 | `hashFor` の出力 |
|---|---|---|---|
| `home` | any | `/` | `/`（`default`） |
| `activity` | any | `/activity` | `/activity` |
| `thresholds` | any | `/thresholds` | `/thresholds` |
| `trends` | `null` | `/trends` | `/trends` |
| `trends` | `'running'` | `/trends/running` | `/trends/running` |

## 却下した案

- **Markdown 整形を自前実装する** — 見出し・箇条書き・強調・引用・リンク・コード・水平線までなら書けるが、
  要件には**表とチェックボックス**が入っている。GFM の表（区切り行・セル内エスケープ・列揃え）と
  タスクリストまで自前で正しく扱うと数百行になり、しかも HTML 生成を伴う実装にするとエスケープ漏れが
  そのまま XSS 経路になる。テスト基盤も無い（`CLAUDE.md` のとおり未導入）ので、壊れたことに気づけない。
- **`marked` + `DOMPurify`** — 合計 min 60KB 程度と `react-markdown` より小さいのが利点。しかし
  (a) `dangerouslySetInnerHTML` が必須になり、サニタイズ設定の正しさをこちらが背負う、
  (b) ハイライトが「描画後の DOM を走査して書き換える」形になり、React の再描画で消える／二重に `<mark>` が入る
  といった事故が起きやすい。`react-markdown` なら (a) の責任が発生せず、(b) も rehype プラグインで
  描画前に解決できる。今回はサイズより安全側を採った。
- **`GET /api/activities` の応答に `note` 本文を載せる** — `ActivityView` / `TrendsView` / `HomeView` の 3 画面が叩く
  共通 API に、その 3 画面が使わない数百 KB を混ぜることになる。要件の「やらないこと」にも該当する。
- **クライアントで `GET /api/activities/:id/note` を件数分ループ** — 100 件で 100 リクエスト。
  要件の「操作を妨げるほど待たされない」に対して分の悪い賭け。
- **サーバー側で絞り込む（`GET /api/notes?q=`）** — ハイライトのためにクライアントにも同じ照合が要るので二重実装になる。
  データ量的にもクライアント照合で足りる。
- **`/api/notes` を `app.use('/api', requireAuth(db))` の手前に置き、ハンドラ個別に `requireAuth(db)` を付ける**
  （`change-password` と同じ形） — 動作としては等価だが、`change-password` が個別指定なのは
  「`/api/auth/*` の並びに置きたいが認証は要る」という位置の都合であって、一般の API に真似する理由が無い。
  付け忘れが即・情報漏洩になる形を、わざわざ増やさない。
- **日記一覧だけ別パスワード／別セッションにする** — 要件の「やらないこと」に明記。
- **`YYYY-MM-DD` をサーバーで組み立てて返す** — コンテナに `TZ` 指定が無く UTC で動くため 1 日ずれる（方針 6）。
- **キーワードを URL ハッシュに載せる（`#/diary?q=LT走`）** — 要件で「戻ったときの復元は不要」と明示されている。
  `parseHash` のクエリ解析を増やすだけ損。
- **`DiaryListView` を `React.lazy` で遅延読み込みして Markdown ライブラリを初期バンドルから外す** —
  初期バンドルは既に plotly で 4.8MB。150KB を切り出すために Suspense 境界を増やす価値が無い。
- **一覧表示時に .fit を先読みしてアクティビティ画面の待ち時間を減らす** — 要件で待ち時間は許容と明記。
  100 件分の .fit（数十 MB）を投機的に取りに行く副作用の方が大きい。
- **`【スイム】` を見出しに変換する独自ルール** — 要件の「GFM の範囲を超える独自拡張記法」に当たる。
  該当の日記は空行区切りの段落として正しく読めるので不要。
- **検索欄の横にヒット件数を出す** — 要件にない UI の追加。「該当なし」の表示だけで足りる。
- **ホーム画面に日記への CTA を足す** — 要件の「やらないこと」に明記（Q17）。

```ts
// 日記一覧の検索まわりの共通処理。一覧の絞り込みと本文のハイライトで同じ正規化を使う。

/** 正規化済み文字列と、「正規化後の位置 -> 元文字列の位置」の対応表。 */
interface Normalized {
  text: string;
  map: number[];
}

/**
 * NFKC 正規化 + 小文字化。大文字小文字と全角半角の違いを吸収する。
 * ハイライト時に元の位置へ戻す必要があるため、1文字ずつ変換して対応表を作る。
 */
function normalize(src: string): Normalized;

/** 入力欄の文字列を検索語の配列にする（空白区切り = AND、空語は捨てる）。 */
export function parseQuery(query: string): string[];

/** すべての語が、いずれかの haystack に部分一致するか（語が0個なら true）。 */
export function matchesAll(haystacks: string[], terms: string[]): boolean;

/** 元文字列上のヒット範囲 [start, end) を、重なりをマージして昇順で返す。 */
export function findRanges(src: string, terms: string[]): [number, number][];

/** ローカルタイム（=JST）基準の YYYY-MM-DD。一覧の日付表示と日付検索に共用する。 */
export function dateKey(iso: string | null): string;
```

実装メモ:

- `normalize` は `for (let i = 0; i < src.length; i++)` で `src[i].normalize('NFKC').toLowerCase()` を連結し、
  **変換後の文字数ぶんだけ** `map.push(i)` する（`㌔` → `キロ` のように 1 文字が複数文字に展開される。確認済み）。
  サロゲートペアは片割れずつ通っても連結で元に戻るので壊れない。
- `parseQuery` は `normalize(query).text.split(/\s+/).filter((t) => t !== '')`。
  NFKC で全角スペースが半角になるので、全角区切りもそのまま通る。
- `matchesAll` は `terms.every((t) => haystacks.some((h) => normalize(h).text.includes(t)))`。
  ※ `haystacks` の正規化を語ごとに繰り返さないよう、先に 1 回だけ正規化して回すこと。
- `findRanges` は `text.indexOf(term, from)` のループで位置を集め、
  `start = map[i]`、`end = (map[i + term.length - 1] ?? src.length - 1) + 1` で元位置に戻し、
  最後に `[0]` 昇順ソート → 重なりマージ。
- `dateKey` は `new Date(iso)` から `getFullYear()` / `getMonth() + 1` / `getDate()` をゼロ埋めして
  `YYYY-MM-DD` を組む（**`getUTC*` は使わない**）。`toLocaleDateString` はロケール任せで書式が変わるので使わない。
  `iso` が `null`／空／`Invalid Date` なら `''` を返す。

### `src/MarkdownNote.tsx`（新規）

```tsx
import { memo, useMemo } from 'react';
import Markdown from 'react-markdown';
import remarkGfm from 'remark-gfm';
import remarkBreaks from 'remark-breaks';
import { findRanges } from './diarySearch';

// hast の最小限の型。@types/hast は react-markdown の推移的依存なので、直接 import せずここで定義する。
interface HastNode {
  type: string;
  value?: string;
  tagName?: string;
  properties?: Record<string, unknown>;
  children?: HastNode[];
}

/** テキストノード1つを、ヒット範囲で text / mark / text … に割る。 */
function splitText(value: string, terms: string[]): HastNode[] {
  const ranges = findRanges(value, terms);
  if (ranges.length === 0) return [{ type: 'text', value }];
  const out: HastNode[] = [];
  let pos = 0;
  for (const [start, end] of ranges) {
    if (start > pos) out.push({ type: 'text', value: value.slice(pos, start) });
    out.push({
      type: 'element',
      tagName: 'mark',
      properties: { className: ['diary-hit'] },
      children: [{ type: 'text', value: value.slice(start, end) }],
    });
    pos = end;
  }
  if (pos < value.length) out.push({ type: 'text', value: value.slice(pos) });
  return out;
}

/** 子ノードを再帰的に走査し、テキストノードだけ差し替える。要素の構造には触らない。 */
function walk(node: HastNode, terms: string[]): void {
  if (!node.children) return;
  const out: HastNode[] = [];
  for (const child of node.children) {
    if (child.type === 'text' && typeof child.value === 'string') {
      out.push(...splitText(child.value, terms));
    } else {
      walk(child, terms);
      out.push(child);
    }
  }
  node.children = out;
}

/** 整形済みツリーのヒット語を <mark> に差し替える rehype プラグイン。 */
function createHighlightPlugin(terms: string[]) {
  return () => (tree: HastNode) => walk(tree, terms);
}

/** 日記本文の整形表示。terms が空配列ならハイライトなし。 */
export default memo(function MarkdownNote({
  source,
  terms,
}: {
  source: string;
  terms: string[];
}) {
  // 検索語が無いときはツリー走査ごと省く。
  const rehypePlugins = useMemo(
    () => (terms.length > 0 ? [createHighlightPlugin(terms)] : []),
    [terms],
  );
  return (
    <div className="diary-body">
      <Markdown remarkPlugins={[remarkGfm, remarkBreaks]} rehypePlugins={rehypePlugins}>
        {source}
      </Markdown>
    </div>
  );
});
```

`remarkPlugins` の配列はモジュールスコープの定数に括り出してもよい（毎回の再生成を避けたい場合）。

### `src/App.tsx`

```ts
export type Tab = 'home' | 'activity' | 'trends' | 'thresholds' | 'diary';

// 既存のコメントブロック（23-28 行）に 1 行足す:
//   #/diary     -> 日記一覧
function parseHash(): Route {
  const segments = window.location.hash.replace(/^#\/?/, '').split('/');
  if (segments[0] === 'activity') return { tab: 'activity', sport: null };
  if (segments[0] === 'thresholds') return { tab: 'thresholds', sport: null };
  if (segments[0] === 'diary') return { tab: 'diary', sport: null };   // ← 追加
  if (segments[0] === 'trends') { /* 既存のまま */ }
  return { tab: 'home', sport: null };                                  // 未知のハッシュは従来どおりホーム
}

// parseHash と対になるよう、入れ子三項をやめて分岐を並べる（出力は従来と同一）。
function hashFor(tab: Tab, sport: string | null): string {
  switch (tab) {
    case 'activity':
      return '/activity';
    case 'thresholds':
      return '/thresholds';
    case 'diary':
      return '/diary';
    case 'trends':
      return sport ? `/trends/${sport}` : '/trends';
    default:
      return '/';
  }
}

function navigate(tab: Tab, sport: string | null = null) {
  window.location.hash = hashFor(tab, sport);
}
```

### 日付

- `dateKey()` では **`getUTC*` を使わない**。`getFullYear()` / `getMonth()` / `getDate()` を使う
  （ローカルタイム = 作者環境では JST）。サーバー側で `YYYY-MM-DD` を作らないこと
  （コンテナに `TZ` の指定が無く UTC で動くため 1 日ずれる）。
- 一覧の日付表示と日付検索は**同じ `dateKey()` の結果**を使う。片方だけ別の整形を使うと受け入れ条件が落ちる。

### データ

- `data/` は実データ。`cde31878c7a31609.note.md` を編集・削除しない。動作確認用の日記は
  アプリの `DiaryCard` から新規に作り、確認後に空保存で消す。
- `curl` 検証や負荷確認は必ず `DATA_DIR` を `/tmp` 以下に切り替えて行う。
  `data/fitviewer.db`（本番のパスワードハッシュとセッションが入っている）を検証用ディレクトリにコピーしない。

## 要件への質問

いずれも実装をブロックしない。設計側の判断で先に埋めてあるので、PM が違うと判断したら差し戻してほしい。

1. **単一改行（ソフトブレイク）の扱い** — 要件に記述が無かったため、`remark-breaks` を入れて
   「書いた改行がそのまま改行として見える」挙動（GitHub のコメント欄と同じ）にした。
   素の GFM 仕様どおり「空行だけが段落の区切り」で良いなら、`remark-breaks` の導入と使用を外すだけで済む
   （`package.json` から 1 行、`MarkdownNote.tsx` から 2 行）。
   なお実データの日記は空行区切りなので、どちらでも既存日記の見え方は変わらない。

2. **一覧に出す指標に平均心拍（bpm）を含めた件** — 要件は「距離・タイムなど規模が分かる数値」としており
   心拍は規模ではないが、「この距離を走ったときに何を感じていたか」を読み返す目的に効くと判断して各種目に加えた。
   不要なら `sportMetrics()` の 1 行を削るだけで外せる。

3. **（報告のみ・回答不要）要件の未確定事項 Q16〜Q18 は、要件書の更新で既定どおり確定したものとして設計した。**
   Q16: タブは ⚡ 閾値 の後ろ（5 番目）。Q17: ホーム画面に CTA は足さない。Q18: 日付は JST 基準。
   加えて、受け入れ条件に「画面に `2026-07-04` と出ているなら」とあることから、
   一覧の日付表示書式は `YYYY-MM-DD` と解釈した（既存の保存済み一覧の `2026/7/4` 形式とは異なる）。
   これが意図と違う場合のみ知らせてほしい。
